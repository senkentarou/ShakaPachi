N≥6のとき、はみ出したウィンドウをどう畳むか

確定済みの設計 — アプリ単位表示 + 選択中アプリのウィンドウをライブプレビューで横並び、タイトルはT4（各ペイン直下に個別タイトル、非選択は不透明度ダウン）、 アスペクト比はR2（16:10の枠内にレターボックス、暗い板で余白を埋める）、選択キーは⌘1〜⌘5固定 — の上で、 N≥6になったときの畳み方だけを3案（X1・X2・X3）で比較します。N≤5では3案とも今日と同じ5枚等幅（270×169）で、差は一切出ません。

パネルは MacBook Pro 14インチ相当（論理解像度1512×982）の画面中央に出る前提で、パネル幅の上限は画面幅から左右40px空けた1432pxです。 ペインの実寸は paneW = (1432 - 40 - 10×(N-1)) / N（floor）、paneH = paneW × 200/320（round）で自分で計算し直しています。 プレビューの中身は単色・グラデーションで埋めず、実際に読める文字列（信号機ボタン・アドレスバー/タイトル・本文行）を持つ偽ウィンドウを実寸で描画し（transform: scale()は不使用）、 フォントサイズもペインの実測サイズに応じてvar(--s)経由で一緒に縮みます。横長（ターミナル）・ほぼ16:10（ブラウザ）・縦長（チャット）・ほぼ正方形（環境設定）の4種を4枚に1回のサイクルで混在させ、 16:10でないものは全てR2のレターボックス（暗い板の余白）が実際に効きます。バッジは⌘1〜⌘5形式で、先頭5枚にだけ付きます。各ペイン・集約タイルはクリックで選択を動かせます。

X1：均等縮小のまま

何枚あっても等幅で並べ続ける

N枚を常に等幅で並べる。バッジは先頭5枚にだけ付き、6枚目以降はバッジなし（矢印キーでのみ辿れる）。位置は常に「左からi番目」で固定だが、大きさはNごとに毎回変わる。

↑ ペインをクリックすると選択だけが切り替わります（大きさはどれも同じなので見た目は変わりません）

  • ⌘1〜⌘5は同じ場所・同じ大きさに居られるか: 場所は常に同じ（先頭5枠から動かない）。しかし大きさはNが変わるたびに全ペイン一律で変わる（N=5: 270×169 → N=12: 106×66）。「押す場所」の記憶は保てるが、「見た目の手がかり」はNが変わるたびに作り直しになる。
  • N=12で実際に何が見えるか: パネル幅1422px、ペイン106×66。ブラウザ系（browser）はタイトルバーの色と見出しの頭文字くらいしか判別できず、ターミナル（横長）はレターボックスの上下帯に挟まれてほぼ文字が消え、チャット（縦長）は左右に大きな暗帯が出て中身は色のブロックにしか見えない。環境設定（正方形）だけはトグル行の形がぎりぎり分かる。
  • パネル寸法の動き: N=5→1430px、N=6→1428px、N=8→1430px、N=12→1422px — 4案中もっとも幅の変動が小さく、常に1432pxの上限内に収まる。選択位置を動かしても幅は一切変わらない。
  • 実装コスト: SwitcherLayoutにNだけで決まる分割関数を1本足せば済み、全ペインが同じ式を共有するのでdraw(_:)の差分再描画も既存どおり「選択移動で2ペイン分の矩形を無効化」のままで足りる。WindowPreviewCacheは既存の選択中±1隣接プリフェッチの延長で足り（先読み対象をN枚に広げるだけ）、新しいキャプチャ経路は不要。4案の中でもっとも実装コストが低い。

X2：フォーカス + 可変サムネ

選択中の1枚だけ常に320×200、残りは可変サムネで分け合う

選択中の1枚は常にネイティブ320×200を維持する。残りは「1432px上限 − フォーカス幅」を(N-1)枚で均等に分け合う可変サムネ（02モックのS4と違い120px固定ではない — N=6ならサムネはまだ204×128、N=12で初めて87×54まで縮む）。選択を動かすとフォーカスとサムネの大きさが入れ替わる。

↑ 任意のペインをクリックするとフォーカスが入れ替わります

  • ⌘1〜⌘5は同じ場所・同じ大きさに居られるか: 場所は変わらないが、大きさは選択位置に強く依存する。選択が先頭5枚の中にある間は、選択中の1枚だけ320×200に膨らみ残りは縮む。ところが選択が6枚目以降に移った瞬間、⌘1〜⌘5の5枚全部がサムネイルサイズに縮む（N=8で143×89、N=12で87×54）。「⌘2を押せば常に同じ大きさの2番目が来る」という前提は、6枚目以降を見ている間は崩れる。
  • N=12で実際に何が見えるか: フォーカス中の1枚（320×200）は完全に読める。残り11枚のサムネ（87×54）は、ブラウザの見出し語頭と環境設定のトグル形状はかろうじて分かるが、ターミナルとチャットはレターボックス帯にほぼ飲まれて判別不能 —「次にどれを選ぶか」をサムネの文字で決めるのはブラウザ系・環境設定系以外では不可能。
  • パネル寸法の動き: N≤5は1430px（X1と同一）、N=6→1430px、N=8→1431px、N=12→1427px — 幅そのものの変動はX1よりさらに小さい（常に上限ぎりぎりに張り付く）。ただし幅が安定している代わりに「サムネ1枚あたりの大きさ」が選択位置のたびに入れ替わるため、中身の伸縮という意味ではX1より落ち着きがない。
  • 実装コスト: SwitcherLayoutに「選択インデックスに応じてフォーカス/サムネの2種類の矩形を返す」関数が要り、X1の「Nだけで決まる純粋関数」より一段複雑（選択インデックスも入力に取る）。draw(_:)の差分再描画は「旧フォーカス→サムネ」「旧サムネ→新フォーカス」というサイズが変わる2枚を再レイアウトしてから再描画する必要があり、単純な矩形無効化では済まない。WindowPreviewCache自体は既存の±1隣接プリフェッチの延長で足り、新しいキャプチャ経路は不要（この点はX1・X3と同程度）。

X3：先頭5枚 + オーバーフロー集約

⌘1〜⌘5は常に270×169固定、6枚目以降は「+K」タイル1個に畳む

⌘1〜⌘5が付く先頭5枚はNによらず常に270×169のまま位置も動かない。6枚目以降は末尾の集約タイル「+K」1個に畳む。←→で6枚目以降に入ると、集約タイルが開いてその窓の実寸ペイン（270×169、⌘なしの通常番号バッジ）に変わり、まだ隠れているものが残っていれば新しい「+K」タイルが続く。

↑ 先頭5枚か集約タイルをクリックすると選択が切り替わります（集約タイルを開いた後は展開されたペイン自身もクリックできます）

  • ⌘1〜⌘5は同じ場所・同じ大きさに居られるか: これが最大の強み。先頭5枚は選択位置にもNにも関わらず常に270×169・常に同じ場所に固定される。⌘1〜⌘5を押したときの見た目は何度押しても完全に同じで、3案の中で唯一、番号キーの筋肉記憶を完全に守れる。
  • N=12で実際に何が見えるか: 先頭5枚は常にN=5と同じ270×169のフル解像度で描画されるため、ブラウザ・ターミナル・チャット・環境設定のどれもN=5と同じ読みやすさを保つ（レターボックスは出るが縮小率はN=5と同一）。集約タイルは「+7」という数字だけで、中身のプレビューは一切見えない — 6枚目以降にどんなウィンドウがあるかは、実際に開くまで分からない。
  • パネル寸法の動き（最大の代償）: N=5の時点で5枚（270×169）+4ギャップだけで既に1430pxとほぼ上限1432pxを使い切っているため、6枚目の存在を示す集約タイルを1個足しただけでパネル幅は約1540pxまで伸び、上限を108px超える。→キーで実際に開く（展開する）と270×169のペインがもう1枚増えるため、N=6（残りなし）で約1710px、N=8/12（残りタイルあり）で約1820pxに達する — MacBook Pro 14インチの画面幅そのもの（1512px）より300px近く広い。中央固定表示のパネルが画面からはみ出す設計は現実的に成立せず、「先頭5枚は縮めない」という主張を守るには、展開時だけ横スクロールを許すか、あるいは展開中は先頭5枚側を犠牲にする（この案が最も避けたかったはずの妥協）が必要になる。
  • 実装コスト: SwitcherLayoutは「先頭5枚は固定関数、6枚目以降は展開状態（何番目を開いているか）を追加入力に取る」構造になり、X1より複雑だがX2ほどではない。draw(_:)は開閉のたびに「集約タイルが消えて実ペインに変わる」「新しい集約タイルが増減する」という要素の種類そのものが入れ替わる変化を扱う必要があり、矩形無効化の単純延長では済まない（01モックの案Aが抱えていたのと同型の複雑さ）。WindowPreviewCacheは表示中の最大6枚（先頭5＋展開中1枚）だけをプリフェッチすればよく、Nに比例して増えないぶんキャッシュ負荷はX1・X2より軽い。
推奨: X1（均等縮小のまま）
実装コストが最も低く、パネル幅が常に1432pxの上限内に収まる — 3案中唯一、画面をはみ出す状態を一切作らない。 X3は⌘1〜⌘5の位置・大きさを完全固定できる点は魅力的だが、その代償としてオーバーフロー展開時にパネル幅が最大約1820pxまで伸び、実画面幅1512pxすら超えてしまう。中央固定表示という設計の前提そのものが壊れるため、現状のままでは採用できない（先頭5枚の枠を最初から少し小さく取り、集約タイル分の余白を確保しておくといった再設計をすれば救えるかもしれないが、それは今回のN=5基準を変えることになり別の検討が要る）。 X2はフォーカス中の1枚は常に読めるが、選択が6枚目以降に移った瞬間に⌘1〜⌘5の5枚が全部サムネイルへ縮み、番号キーの「押した場所に何があるか」という手がかりが3案中もっとも揺らぐ。 X1は「大きさが縮む」という代償を全ペイン均等に払うだけで、位置の予測可能性・実装のシンプルさ・画面内に収まり続けることの3点を同時に満たす、もっとも手堅い選択だと判断した。

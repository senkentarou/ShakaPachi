選択中アプリのウィンドウ縮小戦略：枚数が増えたときの4案比較

「アプリ単位表示 + 選択中アプリのウィンドウをライブプレビューで横並び」という方針の上で、ウィンドウ枚数が 2 / 3 / 5 / 8 枚に増えたときプレビュー1枚あたりをどう縮めるかを4案（S1〜S4）で比較します。 パネルは MacBook Pro 14インチ相当（論理解像度1512×982）の画面中央に出る前提で、パネルが取れる横幅の上限は 画面幅から左右40px空けた1432pxとしています。ペインの中身は単色やグラデーションで塗らず、 実際の8アプリ（VS Code / Safari / ターミナル / Slack / Finder / メール / ミュージック / メモ）を模した偽ウィンドウを 実寸（transform: scale() 不使用）で描画し、フォントサイズも幅に合わせて一緒に縮めています。 同一アプリの複数ウィンドウは本来同じ配色になりますが、判断材料を増やすため意図的に内容密度の異なる8種を混在させ、 どの案でも同じ枚数では同じ内容セット（先頭からN件）を使って比較しています。上段のアプリタイル（76px・8個・先頭が選択中）は どの状態でも同一の文脈チップとして表示しているだけで、下段プレビュー枚数とは連動していません。

ウィンドウ選択バッジ

S1：均等縮小（下限なし）

常にN枚を等幅で並べ、上限1432pxまではそのまま伸び、超えたらひたすら縮む

1枚あたり320×200を基準に、N枚を並べた自然幅が1432pxに収まる間（N≤4）はそのまま320×200のまま。 収まらなくなった瞬間（N=5〜）からパネル幅を1432pxに固定し、以降は (1432-40-10(N-1))/N で ペイン幅がどこまでも縮む。下限を設けていないので、枚数が増えるほど文字は際限なく小さくなる。

↑ ペインをクリックすると選択（タイトル行・強調表示）だけがその中で切り替わります

  • 長所: 実装が最も単純。4案の中で唯一「特別扱いする枚数のしきい値」を持たず、常に同じ1本の式だけで完結する。
  • N=8で読めるか: 165×103まで縮む。VS Codeのコード行やSafariの本文段落は完全に潰れて模様にしか見えず、識別できるのはタイトルバーの色とレイアウトの大まかな形（サイドバーの有無、信号機ボタンの位置）だけ。ターミナルやメモのような「大きい文字1〜2行」中心の画面だけはかろうじて読める。
  • パネル寸法の動き: N≤4では320×200固定で幅704〜1020px・高さ346px。N=5で幅1430px・高さ315pxに、N=8で幅1430px・高さ249pxにジャンプする。中央固定表示のため、4枚→5枚の境界だけ急に幅と高さが同時に変わり視線がついていきにくい。
  • 実装コスト: 既存の previewRect / previewPaneSize(forWidth:) をN分割に置き換えるだけで、幾何計算はSwitcherLayoutに1関数足せば済む。ただし WindowPreviewCache は現状「選択中の1ウィンドウだけ」を前提にしており、この案は表示中のN枚**全部**を同時にキャプチャ・キャッシュする必要がある（N=8なら同時8キャプチャ）。draw(_:) の差分再描画も現状はpreviewRect1枚分の矩形無効化だが、N枚版では選択移動のたびにN枚分（またはハイライトの重なる2枚分）の矩形無効化に変わる。

S2：下限つき + パネル横伸長

1ペイン最小180pxを死守し、足りなければパネルを1432pxの先まで伸ばす

S1と同じ式で縮めるが、ペイン幅が180pxを下回りそうになったら先にパネル幅を1432pxまで広げて確保する。 それでも180pxを維持できない枚数（このデータではN=8）になったら、1432pxの上限自体を超えて パネルを伸ばす — 妥当な下限を守ろうとすると、画面幅の前提そのものを踏み越える様子をそのまま描いている。

↑ ペインをクリックすると選択だけがその中で切り替わります

  • 長所: N≤6程度まではS1と同じ見た目のまま、180px下限のおかげで文字の潰れ方に歯止めがかかる（N=5は270×169でS1と同一、まだ下限を下回っていない）。
  • N=8で読めるか: ペイン自体は180×113とS1の165×103より一回り大きく、サイドバーやタイトルバーの文字はわずかに読みやすくなるが、それでも本文行は依然としてほぼ潰れる。「下限を守った」効果は限定的。
  • パネル寸法の動き: N=8で必要幅が1550pxまで伸び、画面幅から40px余白を取った上限1432pxを118px超過し、MacBook Pro 14インチの画面幅1512pxそのものより38px広い（下の状態にオレンジの点線で両方の基準線を描いている）。中央固定表示のパネルが画面からはみ出す設計は現実的に破綻しており、この案は単独では成立しない（S3のようなページングと組み合わせる前提になる）。
  • 実装コスト: S1の式に max(fitted, minPreviewPaneWidth) を足すだけなのでジオメトリ自体はS1とほぼ同じ差分で済む（SwitcherLayout.effectiveTileSizeの下限クランプと同じ形）。ただしパネルが画面幅を超えるケースをどう扱うか（クランプして結局S1に戻す／画面外にはみ出すのを許容する／自動でS3のページングに切り替える）という**新しい分岐**が要り、キャプチャ枚数の課題はS1と同じくN枚同時。

S3：下限つき + ウィンドウ送り（ページング）

一度に見せるのは最大4枚固定。5枚目以降は横スライドで送る

4枚以下は実枚数に合わせて縮む（S1と同じ挙動）。5枚以上になったら常に4枚ぶんの枠（340×213 — これは 1432pxをちょうど4等分したサイズで、実は単体ネイティブの320×200よりむしろ一回り大きい）に固定し、 選択が右端を越えたら1枚ぶんスライドする。パネルの寸法は5枚でも8枚でも変わらない。

↑ N=5 / N=8 は ◀ ▶ で送りを試せます。オフスクリーン枚数は左右の丸バッジに表示。

  • 長所: 4案中唯一「ペインの最小サイズ」に妥協がない — 何枚あっても表示中の4枚は常に340×213を維持する。パネルの寸法もN=5とN=8で完全に同一（幅1430px・高さ359px）なので、5枚以上のレンジでは中央固定表示でも視線が迷わない。
  • N=8で読めるか: 表示中の4枚は340×213とS1のどのケースよりも大きく、VS Codeのコード行やSlackのメッセージも短い単語なら判別できる。ただし「読めるのは常に4枚だけ」で、残り4枚は送らないと見えない — 読みやすさの代償として一覧性を犠牲にしている。
  • パネル寸法の動き: N≤4では320×200（S1と同じ、高さ346px）、N≥5になった瞬間に340×213・高さ359pxに切り替わる。4→5の境界だけ段差があるのはS1と同じだが、5以降は一切変化しないぶんS1より予測しやすい。
  • 実装コスト: ジオメトリは SwitcherLayout の純関数だけで表現できる（表示ウィンドウ数をmin(count, 4)にクランプし、オフセットはselectedIndexから導出する1変数を足すだけ）。WindowPreviewCache 側は「画面に出ている最大4枚だけを同時キャプチャすればよい」ため、S1/S2のようにNに比例してキャプチャ枚数が増えない — 4戦略の中でキャッシュ設計が最も軽い。draw(_:) は送り操作のたびに表示中の4枚全部を再描画する必要があり、既存の「2タイル分の矩形無効化」では足りず、送りアニメーション込みならCore Animationのレイヤー移動に寄せたほうが自然（現状のCPU再描画路線から外れる）。

S4：フォーカス + フィルムストリップ

選択中の1枚だけ320×200のまま、他は120×75の小サムネで左右に並ぶ

選択中の1枚は常にネイティブ320×200を維持し、非選択の残りは120×75のサムネイルとして左右に並ぶ。 選択を動かすとフォーカスとサムネイルの大きさが入れ替わる。パネル幅は枚数に応じて伸びるが、 今回の最大N=8でもまだ1432pxの上限には届かない（後述）。

↑ 任意のペイン（フォーカス・サムネイルどちらも）をクリックするとフォーカスが入れ替わります

  • 長所: 選択中の1枚は常にネイティブ320×200 — 4案の中で「今見ている1枚」の読みやすさが唯一劣化しない。パネルの高さはどのNでも常に346pxで固定（フォーカスが常に一番背が高いペインのため）。
  • N=8で読めるか: フォーカス中の1枚は完全に読める。ただし残り7枚のサムネイルは120×75しかなく、タイトルバーの信号機ドットと配色でアプリの見当はつくが、本文の文字列はどのアプリでも実質的に読めない — 「次にどれを選ぶか」をサムネの文字で判断するのは不可能で、色とレイアウトの記憶に頼ることになる。
  • パネル寸法の動き: 幅はN=2で704px→N=8で1270pxまで単調に伸びる（320+(N-1)×130+40）。上限1432pxに触れ始めるのはこの式からN≈10前後で、今回の実験レンジ（〜8枚）ではまだ余裕があるが、10枚を超えるアプリ（Safariのタブが多いケースなど）では結局S3同様の送りに切り替える設計にせざるを得ない。
  • 実装コスト: ジオメトリはS3よりむしろ複雑 — 「選択中の1枚だけ320×200、他は120×75」という**2種類のペインサイズ**を同時に扱う必要があり、SwitcherLayoutに新しいレイアウト関数（フォーカス幅+Σサムネ幅+ギャップ）を1本足すだけで済む点はS3と同等。ただしWindowPreviewCacheは「フォーカス中の1枚は高解像度、残りは低解像度サムネで十分」という**2段階のキャプチャ品質**を持ち込むことになり、キャッシュのキー設計（同じウィンドウでも解像度違いの2枚を持つか、都度リサイズするか）がS1〜S3のどれよりも複雑になる。draw(_:)の差分再描画も、選択移動のたびに「旧フォーカス→サムネ」「旧サムネ→新フォーカス」の**サイズが変わる2枚**を再レイアウトしてから再描画する必要があり、単純な矩形無効化では済まない。
次の判断ポイント: 4案のうちどれを採るか。
推奨は S3（下限つき + ウィンドウ送り）。 理由は3つ。(1) 読みやすさの底が最も高い — 表示中の4枚は常に340×213を維持し、S1/S2のようにN=8で165〜180pxまで潰れることがない。 (2) パネル寸法がN=5以降で完全に一定（幅1430px・高さ359px固定）になり、中央固定表示という制約と最も相性がよい — S1のように4→5枚で急にジャンプしたり、S2のように画面幅そのものを超えて破綻したりしない。 (3) WindowPreviewCacheへの負荷が最小 — 画面に出ている最大4枚だけを同時キャプチャすればよく、Nに比例して キャプチャ枚数が増えるS1/S2や、2段階の解像度を持ち込むS4より実装・メモリの両面で安全側に倒せる。 唯一の代償は「一覧性」（8枚全部を一目で見渡せない）だが、それはS4も同程度に抱える制約であり、S3固有の弱点ではない。
